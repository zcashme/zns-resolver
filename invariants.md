# ZNS Resolver — Invariants

- DB written once per block (single writer)
- DB read on every API call (many readers, concurrent)
- Sync module streams blocks from lightwalletd, tracks tip, detects reorgs
- Orchard decryption with FVK (from UFVK, for both incoming + OVK self-send) yields candidates
- OVK self-send proof required (anti-impersonation) — incoming-only notes rejected
- Binding verification: prove on-chain cmx commits to (name, ua, prev_rcm)
- Per-name chain integrity: claim -> update* -> release, prev_rcm->rcm linkage
- Lifecycle admission control: legal transitions only, reject notes not extending our tip
- Memo format parsing + name validation (ZNS: prefix, validate_resolver_name)
- Checkpoint atomicity: scan_state advances in same tx as batch's events
- Restart idempotency: crash anywhere -> read checkpoint -> resume, no re-index gap
- Reorg rewind: roll back events past fork, rebuild affected name tips from surviving history
- Deep reorg fallback: nuke + rescan from birthday (current threshold >30 blocks)
- Lightwalletd is untrusted external boundary: reorgs, stream breaks, malformed blocks must not corrupt the index
- Sync failures degrade to retry/reconnect, never write garbage
- JSON-RPC read API (resolve, status, events)
- Status is derived only from the persisted checkpoint + name count (no live in-memory status)
- UFVK is the registry's viewing key (decrypt + OVK proof)
- Names table = live tips; name_events table = full history
- name_events PK includes (name, height) — latent bug: should include action_index (collision -> batch abort -> sync spin)
- One write path: apply_batch (events + names upsert/delete + checkpoint, one tx)
- One read path: resolve_by_name, registrations_by_ua, list_registrations, events, name_count, checkpoint, registry_ufvk
- Read consistency model: readers must not see half-applied batches (serializable-equivalent)
- Backpressure: bounded queue between producers and DB
- Shutdown: graceful drain, no orphaned in-flight ops
- All crypto (decrypt + binding verify + OVK proof) currently runs on DB thread inside the tx (latency cost)
